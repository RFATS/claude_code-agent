# Router 패턴 가이드

## Router란?

앞 단계의 결과나 입력 조건에 따라
다음에 실행할 AI Task를 다르게 선택하는 패턴입니다.

모든 입력을 같은 AI가 처리하는 것이 아니라,
유형·상태·기준값·판단 결과에 따라
서로 다른 AI Task 또는 Sub Agent를 호출할 수 있을 때 사용합니다.


## Router의 기본 구조

Router의 분기 조건은
앞 단계의 코드 결과에서도, AI의 판단 결과에서도 나올 수 있습니다.

예시 1. 코드 결과에 따라 AI 호출

[코드: 상태 판정]
        ↓
   정상 / 지연 / 위험
    ↙     ↓      ↘
 [종료] [AI A]  [AI B]


예시 2. AI 판단 결과에 따라 AI 호출

[AI: 이슈 분류]
        ↓
  품질 / 비용 / 일정
    ↙     ↓      ↘
 [AI A] [AI B]  [AI C]


## 분기 조건 찾기

업무설계서와 현재 Workflow에서
"어떤 결과에 따라 다음에 할 AI 작업이 달라지는가?"를 찾습니다.

분기 조건은 다음 4가지 관점에서 확인합니다.


### 1. 유형

입력이나 대상의 종류에 따라
다른 AI 작업이 필요한 경우입니다.

예시
- 문의 유형: 제품 / 배송 / 환불
- 문서 유형: 계약서 / 견적서 / 사양서
- 이슈 유형: 품질 / 비용 / 공급


### 2. 상태

앞 단계에서 판정된 상태에 따라
다른 AI 작업이 필요한 경우입니다.

예시
- 납기 상태: 정상 / 지연 / 위험
- 처리 상태: 신규 / 진행 중 / 완료
- 검토 상태: 확인 필요 / 이상 없음


### 3. 기준값

업무에서 사용하는 기준값이나 임계값에 따라
다른 AI 작업이 필요한 경우입니다.

예시
- 불량률 기준 초과 / 이하
- 납기 지연 기준 초과 / 이하
- 목표 달성률 기준 이상 / 미만

업무설계서에 없는 숫자나 기준값을
임의로 만들지 않습니다.


### 4. 판단 결과

AI가 내용을 분석하거나 분류한 결과에 따라
다른 AI 작업이 필요한 경우입니다.

예시
- 원인 판단: 설비 / 자재 / 공정
- 리스크 판단: 기술 / 비용 / 일정
- VOC 분석: 품질 / 가격 / 서비스


## 분기 조건은 앞 단계에서도 찾기

Router의 분기 조건이
반드시 AI Task 안에 있을 필요는 없습니다.

앞 단계의 코드나 AI가 이미 분류·판정한 결과가 있다면
그 결과를 다음 AI를 선택하는 조건으로 활용할 수 있습니다.

예시:

[코드: 상태 판정]
        ↓
  ┌─────┼─────┐
 정상   지연   위험
  ↓      ↓      ↓
 종료  [AI A] [AI B]

따라서 AI Task만 개별적으로 보지 말고,
앞 단계에서 어떤 결과가 만들어지는지도 함께 확인합니다.


## Router 추천 기준

업무설계서와 현재 Workflow를 보고
조건에 따라 서로 다른 AI Task 또는 Sub Agent를 호출할 수 있는 부분을 찾습니다.

다음 기준으로 검토합니다.

1. 앞 단계의 결과 또는 AI의 판단 결과에 구분 가능한 조건이 있는가?
2. 조건을 유형 / 상태 / 기준값 / 판단 결과로 표현할 수 있는가?
3. 조건에 따라 서로 다른 AI 작업을 호출할 수 있는가?
4. 분기 조건을 업무설계서의 입력 자료, Process, 업무 기준에서 확인할 수 있는가?

조건에 따라 다음 작업이 달라지지 않는다면
Router로 추천하지 않습니다.

단순히 여러 작업을 동시에 수행하는 경우는
Router가 아니라 Parallel에 해당합니다.

업무설계서에 없는 조건이나 기준값을
임의로 만들지 않습니다.


## 추천 원칙

Router를 적용할 가능성이 있는 부분을 찾아 추천합니다.

추천한 Router를 실제 Workflow에 반영할지는
사용자가 판단합니다.

Router 구조를 임의로 확정하거나
기존 Workflow에 바로 반영하지 않습니다.

추천할 만한 Router가 있다면
어떤 조건으로 어떤 AI가 호출되는지 보여준 뒤
사용자에게 반영 여부를 확인합니다.

적합한 Router가 없다면
억지로 분기 조건이나 새로운 AI Task를 만들지 않습니다.


## Workflow 시각화 원칙

Router를 검토할 때는
`workflow.md`에 저장된 현재 Workflow를 기준으로 합니다.

코드 / AI / 사람 Task를 모두 포함하여
현재 Workflow에서 Router가 어디에 들어가는지 알 수 있도록 보여줍니다.

기존 Workflow의 Task나 연결 관계를
임의로 삭제하거나 변경하지 않습니다.

이전 단계에서 Parallel 등 다른 패턴이 이미 반영되어 있다면
그 구조도 그대로 유지합니다.


## 결과 표현 방법

길게 분석하거나 체크리스트 형태의 검토표를 출력하지 않습니다.

다음 순서로 간단하게 보여줍니다.


### 1. 현재 Workflow

`workflow.md`에 저장된 현재 전체 Workflow를
상자와 화살표로 시각화합니다.


### 2. Router 추천

Router를 적용할 수 있는 부분이 있다면
다음 내용만 간단히 설명합니다.

- 대상 부분
- 분기 조건
- 조건별로 호출할 AI
- 추천 이유


### 3. 추천 구조 시각화

추천한 Router를 적용했을 때
Workflow가 어떻게 달라지는지 상자와 화살표로 보여줍니다.

기존 Parallel 구조 등 이미 확정된 Workflow는 유지하고,
추천하는 Router 부분만 추가하여 보여줍니다.

예시:

[코드: 상태 판정]
        ↓
  ┌─────┼─────┐
 정상   지연   위험
  ↓      ↓      ↓
 종료  [AI A] [AI B]


## 사용자 확인

추천한 Router 구조를 바로 확정하지 않습니다.

추천 결과와 전체 Workflow를 보여준 뒤
사용자에게 다음과 같이 확인합니다.

"이 Router 구조를 Workflow에 반영할까요?"

사용자가 수정을 요청하면
요청한 내용을 반영하여 구조를 다시 보여주고 확인받습니다.


## Workflow 확정 및 저장

사용자가 Router 구조를 확정하면
추천한 Router를 현재 Workflow에 반영합니다.

기존 `workflow.md`에 저장된 내용과
이미 확정된 Parallel 등의 구조는 그대로 유지합니다.

Router가 반영된 전체 Workflow를 다시 정리하고,
현재 폴더의 `workflow.md` 파일을 업데이트합니다.

`workflow.md`에는 최소한 다음 내용을 유지합니다.

- 전체 Task의 실행 순서
- 각 Task의 실행 주체: 코드 / AI / 사람
- 확정된 Parallel 구조
- 확정된 Router 구조
- Task 간 연결 관계
- 전체 Workflow 시각화

사용자가 확정하기 전에는
`workflow.md`를 수정하지 않습니다.
