# fail 대응 리포트 작성 규칙

형식 기준은 `reference/example.html`이다. 구조·스타일·완성도를 그대로 따르되, 내용은 해당 알림의 산출물로 채운다. 예시의 내용을 옮겨 적지 않는다.

## 파일
- standalone HTML 1개 (외부 파일·스크립트 없음, 인라인 CSS)
- 저장 위치: `output/alert-NN/report.html`, 알림 1건당 1개

## 헤더
- 소속 · 리포트 제목(`DAG / Task`) · 생성 일시
- 배지: 판별 결과(진성 fail / 가성 fail) · 원인 요약 · 검증 결과(진성만) · 승인 상태(항상 "사람 승인 대기")

## 섹션 (번호 고정)
1. **알림 정보 및 진성/가성 판별** — DAG, Task, Logical date, 최종 fail 시각, 판별 결과, 판별 근거(에러 유형·재시도 이력), 참고한 과거 사례(case_id, 승인/불승인, 어떻게 참고했는지)
2. **진성 fail 원인 분석** — 근본 원인, 에러 발생 위치, fail 기간, 영향 테스터, 영향 LOT, 후속 영향, 수정 방침
3. **수정 코드 변경 내역** — 파일명과 변경 전/후 diff (추가 줄·삭제 줄 구분), 택하지 않은 방식과 이유
4. **검증 결과 및 배포 승인 요청** — 일자별 검증 표(입력 행 수, 수정 전, 수정 후, 결과), 검증 항목 통과 수, PR 설명 요약(제목·변경 파일·재처리 필요 여부), merge 승인 체크 항목, 승인/보류 버튼 영역

## 가성일 때
- 1번 섹션만 채운다.
- 2~4번 섹션은 제목을 유지하고 본문에 "해당 없음 (가성 fail로 판별되어 조치 대상이 아님)"만 표시한다.
- 승인 요청 대신 "조치 없음 종결 확인" 항목(재시도 성공 확인, 결과 건수 확인 여부)을 1번 섹션 끝에 체크 항목으로 둔다. 로그로 확인되지 않은 항목은 체크하지 않고 "확인 필요"로 표시한다.

## 작성 원칙
- 수치·사실은 산출물(context / classification / analysis / fix_summary / verification JSON)의 값만 옮긴다.
- 확인되지 않은 항목이나 검증 FAIL은 숨기지 않는다. 검증이 FAIL이면 배지를 경고로 바꾸고 "보류 권장"을 표시한다.
- 최종 결정은 사람이 한다. 승인 상태는 "승인 대기"로 표시한다.
- 코드 diff는 원본(`data/dags/`)과 수정본(`output/alert-NN/fixed/`)을 비교해 작성한다.
- 설명은 짧게, 표와 배지 위주로 쓴다.
